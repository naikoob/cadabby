# Vault Style & Voice Guidelines

* **Voice**: Authoritative, analytical, objective, and dense. Avoid conversational filler, throat-clearing, and sycophantic intros.
* **Epistemic Honesty Over Completeness**: Write only what the cited `raw/` sources and linked vault notes establish. Never silently extrapolate benchmarks, SLAs, architectural guarantees, or dates from general model knowledge to make a note look complete; omit unattested details or record them as explicit open questions. Step-by-step arithmetic evaluations of source-attested formulas are permitted; when the user explicitly requests supplemental explanations not present in `raw/`, fence them inside a `> [!WARNING] Unverified Supplement (not attested in raw/)` callout and leave the note `unverified`.
* **File Naming & Titles**:
  - **Lowercase `kebab-case` Stems**: Name note files with singular, lowercase noun phrases separated by hyphens (e.g., `flash-attention.md`, `epistemic-trust-tiers.md`, `sqlite-vs-duckdb.md`). Lowercase `kebab-case` eliminates acronym and preposition casing ambiguity in case-sensitive link resolution, requires no shell quoting in CLI workflows, and prevents case-only Git rename collisions across Linux, macOS, and Windows.
  - **Stem vs. Frontmatter `title`**: Keep the filename stem concise and lowercase (`flash-attention.md`); use the frontmatter `title` field for the full capitalized display title (`title: "Flash Attention: IO-Aware Exact Attention"`).
  - **MOC & Hub Suffixes**: Suffix Maps of Content (`type: moc`) in `wiki/` with `-moc.md` (e.g., `storage-moc.md`, `ai-systems-moc.md`) so entry points stand out when listing or filtering a 1,000+ note flat directory. In cognitive domains (`customers/`, `projects/`), name folder hubs `README.md` or `{topic}-moc.md` — never `index.md`, which is reserved for the root engine-generated gap report.
  - **No Metadata Prefixes**: Never encode note type, lifecycle status, or dates into `wiki/` filenames (avoid `concept-sqlite.md`, `draft-attention.md`, `2026-10-09-sqlite.md`). Taxonomy and lifecycle state belong in OKF frontmatter (`type`, `status`, `tags`) so evolving a note never forces renames or breaks inbound links.
  - **Semantic Disambiguation**: When two concepts in `wiki/` share a base name, disambiguate with a domain or system qualifier (`sqlite-wal.md` vs. `postgresql-wal.md`), never with sequence numbers or opaque hashes (`wal-2.md`, `wal-8f3a.md`). Notes sharing a stem across different cognitive domains (`wiki/architecture.md` and `projects/apollo/architecture.md`) need no filename suffix; disambiguate at the link site with a path prefix (`[[apollo/architecture]]`).
* **Cross-Linking**: Generously link entities and concepts using `[[wikilinks]]` or `[[wikilinks|Aliases]]`. Inside Markdown table cells, escape the alias pipe as `\|` (`[[wikilinks\|Aliases]]` or `[[wikilinks#Section\|Aliases]]`) so it does not split the table column; the link resolver strips the escape backslash automatically. Relative Markdown note links (`[Label](../wiki/note.md)`) are accepted and checked like wikilinks, but prefer wikilinks: they survive moves and need no `../` depth.
* **OKF Frontmatter**: Every note across all cognitive domains (both `wiki/` and custom domains like `customers/` or `projects/`) must begin with strict YAML frontmatter specifying `type`, `title`, `description`, and `status`.
* **Tags**: Lowercase kebab-case, with `/` for hierarchy (e.g. `knowledge-base`, `trust/human-reviewed`). Tags must never contain whitespace — write `machine-learning`, not `machine learning` — because a tag with a space silently breaks `--tag` filtering. Casing is normalized on write; whitespace is rejected outright.
* **Governance**: Consult `AGENTS.md` for cognitive domain manifests, epistemic trust tiers, and operational rules.
